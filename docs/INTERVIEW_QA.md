# 个人作品集网站：面试问答

更新日期：2026-09-16。围绕本仓库实际完成的网站工作整理。以下回答可用于口述，技术数字以 [验收记录](RELEASE_20260916.md) 为准。

## 30 秒介绍

我做了一个面向求职和博士申请的个人研究与生活作品集。它把分散的研究、论文、实践和影像整理成有层次的网页，面试官可以从首页快速了解我，再进入项目查看工作、结果和依据。这个项目同时涉及内容建模、React 页面工程、视觉与动效、可访问性以及公开仓库的隐私保护。我主导需求、内容核验和设计选择，借助 Codex 完成实现与验证。

## 两分钟介绍

最初的需求是给简历补充一个能深入了解我的入口。原始资料很多，但直接上传文件既难阅读，也可能暴露不适合公开的信息。

我先按照访客的阅读顺序整理内容：主页讲定位，栏目页提供入口，详情页讲问题、个人贡献、方法和结果。论文状态和实验条件保留在内容结构里，生活部分用真实照片和长期记录补充个人面貌。

技术上使用 React、TypeScript 和 Vinext / Vite，部署在 Cloudflare Sites。首页是天文主题，动画和生活栏目分别有适合内容的布局。动效可以跳过和暂停，并响应系统减少动态；移动菜单还需要处理键盘焦点与滚动恢复。

工程上，我补上路由、链接、图片、元数据和内容口径的自动检查，并通过 Git 维护可以复现的源码。这让我练习了从真实需求、设计取舍到可运行交付的完整过程。下一步是否增加后台或更复杂功能，会看内容更新频率和实际使用反馈。

## HR 常见问题

### 1. 为什么要做这个项目？

一页简历能概括经历，但讲不清一项研究具体做了什么。我希望面试官和潜在导师能按自己的兴趣继续阅读，同时看到我在科研之外持续投入的事情。网站把分散材料组织成了一个稳定入口。

### 2. 目标用户是谁，解决了什么问题？

主要是招聘方、潜在博士导师和研究同行。他们时间有限，需要快速判断研究方向、个人贡献和表达能力。我用“概览—索引—详情”的层次减少查找成本，并把结果条件和来源保留在具体内容旁边。

### 3. 你具体负责什么？

我负责提出需求、提供并核对资料、确定受众、选择设计方向、决定公开范围和验收标准。实现和测试过程中使用了 Codex 辅助。我会沿着数据结构、页面模板和关键交互解释这些决策，以及它们如何落实到代码。

### 4. 使用 AI 辅助后，如何体现你的能力？

工具能加快实现，但不能替我决定哪些经历值得展示、材料是否准确、私人资料是否可以公开，也不能替我承担上线后的内容责任。我的工作是把需求说清楚、识别错误输出、提出可验证的验收标准，再根据实际结果调整。面试时可以直接看具体页面和代码，讨论这些选择。

### 5. 最值得讲的亮点是什么？

我会讲三个相互联系的点：把内容可信度写进数据结构；在共同设计系统里区分研究、动画和生活的表达；让动效、可访问性、验证和隐私保护成为交付的一部分。这些共同服务于“容易了解，也经得起核对”的目标。

### 6. 项目是否真的落地？

网站已经有公开访问地址，内容来自真实经历，也有可以安装、运行和验证的源码。当前能确认的是这些实际交付；还没有建立访问量或求职转化的统计，因此我不会用没有依据的业务数字描述效果。

### 7. 做过哪些取舍？

我保留了有识别度的开场和主题动效，同时让它们可跳过、可暂停，并减少正文中的持续动画。内容更新频率不高，所以先使用类型化记录维护，没有为了完整感增加账号、数据库和后台。

### 8. 遇到过什么具体困难？

一个有代表性的问题是移动菜单曾被页头的背景滤镜限制，展开后只显示在页头高度里。通过浏览器检查定位到固定定位与包含块的关系，在移动断点去掉相关背景滤镜，再验证菜单覆盖、Escape、焦点和滚动恢复。修复不只看截图，还要验证操作链条。

### 9. 这个项目与研究经历有什么联系？

研究训练要求我把问题、方法、结果和证据讲清楚，网站则把这种结构变成了访客可以操作的阅读路径。对实验条件、个人分工和来源的检查，也直接影响内容模型和测试设计。

### 10. 为什么还展示生活与动画？

招聘和申请首先看专业能力，但长期兴趣和实践也能体现表达、持续投入和观察力。我把它们放在独立栏目里，访客可以选择继续了解，首页仍然优先提供研究入口。

### 11. 如何体现创新性？

这项工作的创新主要是针对具体需求的整合：内容的可信表达、按内容类型组织体验、以及公开交付的资料边界。使用的框架和动效库都有成熟来源，我更愿意展示如何解决问题、如何验证取舍，而不是将采用这些库称为算法创新。

### 12. 如果继续迭代，先做什么？

优先看实际阅读反馈和更新负担。若访问者找不到关键信息，就优化入口；若维护频繁，再考虑内容后台；若首屏加载成为问题，则以相同条件测量后压缩资源、推迟非必要交互。每一步都对应一个实际问题。

## 技术面试追问

### 13. 技术栈为什么这样选？

沿用现有的 React 19、TypeScript 和 Vinext / Vite，可以复用页面与交互代码。类型适合约束项目、论文、经历等内容字段；组件适合复用详情结构。Cloudflare Sites 已承载线上网站，继续使用能减少迁移带来的额外问题。

### 14. 整体架构怎么讲？

从公开内容数据开始：记录进入栏目和详情模板，生成服务端页面、元数据和站点地图；浏览器再接管菜单、开场与其他交互。图片放在本地公开资源目录。源码通过 Git 维护，验证通过后再按独立的托管流程部署。

### 15. 为什么不把所有内容直接写在页面里？

一个项目会出现在首页、项目索引、详情和相关链接中。将内容集中成记录，可以复用事实并降低复制后的不一致。论文状态和个人职责变更时，也更容易知道应该修改哪里。

### 16. 类型检查能保证事实正确吗？

类型能防止字段缺失和结构误用，事实仍要靠来源核验。这里结合了人工核对、状态字段和回归断言，例如保持污水能耗论文为 Water Environment Research 在审，防止页面改版时误写成已发表。

### 17. 为什么使用原生链接？

每个详情页都应有可直接打开的地址，浏览器的返回、复制链接与无脚本阅读也应该自然工作。此外，原生导航是这个项目经过验证的部署兼容要求，因此没有在收尾时随意替换导航方式。

### 18. 动效由哪些部分构成？

Motion 负责约 3.2 秒的首页开场和摄影预览；CSS 承担轻量装饰与状态过渡；Canvas 承担主题环境效果。React Bits 只选用了少量文字和边框组件。正文的阅读顺序与含义不依赖动画。

### 19. 怎么避免动画影响使用？

首先让开场可以跳过，并支持 Escape。其次提供统一动态开关，尊重系统减少动态设置。Canvas 限制约 30 fps 和像素比，并在离屏、后台或开场覆盖时停止绘制。无脚本时正文仍可以阅读。

### 20. 移动菜单为什么需要单独处理焦点？

菜单打开后，键盘操作应留在当前对话框内，背景内容不能继续获得焦点。关闭时应返回触发按钮，并恢复原来的滚动位置。否则用户虽然看得到菜单，实际操作会跳到背景或页面顶部。

### 21. 你们怎么测试？

先运行构建、Lint 和 TypeScript，再从构建出来的 Worker 渲染页面，检查状态码、内容、内部链接、图片、元数据和旧地址跳转。浏览器测试补上静态 HTML 无法证明的菜单、动效、焦点和响应式行为。现有页面回归共 28 项测试。

### 22. 一百多个页面是否都写了独立代码？

不是每个地址都对应一份独立页面实现。很多地址由项目、文章和年份数据配合详情模板生成。复杂度主要来自不同内容类型、状态与交互的共同维护，因此测试既覆盖代表性模板，也覆盖实际地址。

### 23. 做了哪些性能工作？

使用响应式图片、明确图片尺寸、首屏之外的懒加载、轻量 CSS，以及动画的可见性控制。曾把正文页的轻量装饰从 Motion 组件分离，减少不必要代码。效果需要看实际测量：上一轮开场增加后，三次受限网络测量的首页 LCP 中位数有所增加，因此不能把整体视觉升级称为提速。

### 24. 能举一个具体性能数字吗？

在上一轮同设备、4 倍 CPU 限速、4 Mbps 下载和 40 ms 延迟的三次测量中，桌面首页 LCP 中位数由 2.360 秒到 2.740 秒，测量窗口内传输量约由 767 KB 到 988 KB。案例页和年度总表的布局偏移有所改善。这组数字只说明指定条件下的变化，不能代表真实用户总体体验，也不是 INP。

### 25. 为什么 `.gitignore` 不够？

它主要影响未跟踪文件，不能移除已经提交的内容。一份敏感文件即使从最新版本删除，仍可能从旧提交中读到。所以需要检查即将公开的分支及其可达历史，并审查远端附件、讨论和工作流记录。私人旧历史备份保留在本地，不能用镜像推送带到远端。

### 26. 上传检查具体覆盖什么？

已有脚本检查待推送分支的历史路径和常见文本文件中的凭据格式，配合项目既有的忽略规则。它不能识别所有业务语义，也不代表对所有二进制文件做过完整审计。网站所展示的个人介绍、经历与照片可以公开使用。

### 27. 为什么私人文件加密后也不上传？

项目运行并不需要它们。将资料留在本地可以缩小公开范围，也避免未来密钥泄露或误解密带来的风险。这里采用的策略是公开内容独立构建，原稿与私人备份本地隔离。

### 28. 如何从零运行？

检出 `codex/portfolio-release`，安装 README 规定的 Node.js，执行 `npm ci` 和 `npm run dev`。本地阅读不需要 API Key 或数据库。运行 `npm test` 可以重建并检查页面；Lint 与 TypeScript 命令见 README。

### 29. GitHub 同步是否会直接发布网站？

源码同步与 Sites 部署是两个操作。当前仓库可以本地运行自动测试，但没有配置 GitHub 自动部署。本次把已上线的网站源码同步到开发分支，并通过 README 和 About 链接到网站；没有合并 main 或新建站点。

### 30. 目前有哪些边界？

当前主要是个人内容展示，没有 CMS、在线编辑和用户数据业务。移动视口验证不等于真实手机验证，抽样对比度检查不等于完整可访问性认证。还没有稳定的访问统计或求职效果测量。继续建设时，我会根据实际使用问题决定优先级。

## 面试前的五项准备

1. 实际运行一次项目，熟悉 README 的安装和验证命令。
2. 打开一个内容记录及对应详情模板，能解释数据如何进入页面。
3. 演示移动菜单、开场跳过和动态开关，理解焦点与滚动恢复。
4. 看一条页面回归测试，解释它验证了什么，以及哪些交互还需要浏览器验证。
5. 核对最新分支、在线版本和测试结果，口述中区分本人的决策、工具辅助以及未经验证的效果。
